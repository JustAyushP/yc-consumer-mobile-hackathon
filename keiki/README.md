# Telegram common-character consult demo

`agent.ts` contains an isolated neutral prompt, the `consult_ravo` webhook-tool configuration, and `setLinePrompt({externalRef, consultUrl, lineId, telegramBotId})`. The helper reads server-only `KEIKI_API_KEY`, disables group chats, and upserts by external reference with `channels: []`. It never reads a bot token or creates/attaches channels. It accepts no private prompt and refuses the existing `ravo-common` standalone character. It is not invoked automatically.

The demo uses the **legacy webhook-tool** contract documented in [Keiki's billing example, section 2](https://onkeiki.com/docs/billing-agent-example): `X-Orchid-Api-Key`, `X-Orchid-Trace-Id`, and `{input, context: {phone, channel: "telegram"}}`. `context.phone` is an opaque platform conversation identity, not a model argument or necessarily a phone number. The server pins one Telegram bot, one exclusive Keiki agent/key, and logical line `1`; groups are unsupported. No provider bot-id field is invented: the static tool URL's `botId` is our operator-controlled mapping, not independent provider evidence.

This is **not** the signed identity-webhook or Ed25519 external-harness protocol. Signed tool mode omits the legacy key header; it is not silently accepted here. `/keiki/turn` remains disabled. Before a live legacy-tool test, use a deployment key exclusive to this demo agent (not reused for other agents) and inspect an isolated tool payload: the newer [conversation-auth docs](https://onkeiki.com/docs/conversation-auth) promise richer signed context but do not publish its complete wire shape. The legacy envelope has no documented agent-id field, so the configured agent is a fixed single-agent assumption, not an independently verified payload field. Never copy model-provided identity IDs into bindings.

The ingress starts disabled. Server configuration is `KEIKI_TOOL_API_KEY`, `KEIKI_DEMO_AGENT_ID`, `KEIKI_DEMO_LINE_ID=1`, `KEIKI_DEMO_TELEGRAM_BOT_ID` (verified numeric bot id), and explicit `KEIKI_DEMO_INGRESS_ENABLED=true`. Enable only under coordinated test authorization after inspecting actual context and the key's exclusive use. The tool URL is `/keiki/consult?lineId=1&botId=<configured id>`; both values must exactly match server configuration. Pre-provision one active binding across agent, channel `telegram`, `conversationId=JSON.stringify(["telegram", configuredBotId, context.phone])`, `senderId=context.phone`, and line `1`, with a known matching player/group. This is local namespacing, not proof that Keiki separates histories by bot. No model identity IDs, phone lookup, or join flow are accepted. Completed, pending, and uncertain traces return 409 without automatic re-consult; completed directives are not redelivered.

Trace-based dedupe suppresses repeats of a known tool call, not every redelivery of a provider message under a different trace. The model supplies `playerMessage`; without a verified provider transcript this is not proof of verbatim transport text. No exactly-once game-effect guarantee is claimed. Pending or uncertain receipts require manual investigation, not automatic retries.

Fresh delivery calls Brain's read-only `internal.ravo.consult.authorizeCachedDirective` with the full directive inside the completion mutation, sharing its transaction with binding checks and receipt completion. Denial or query failure returns 503, keeps the receipt uncertain where possible, and never retries consult. This depends on the Brain runtime helper and is not an atomic external-delivery guarantee. Freeform tool text does not create a structured answer, credit progress, or unlock evidence. With no reviewed character sheet the current runtime can authorize generic Sal guidance; character facts/reveals still require reviewed knowledge. Public cross-player labels and unanswered questions follow Brain's independent eligibility checks.

Offline tests label fake transport/master/authorization and separately exercise real scripted Brain consult/authorization. They do not prove Keiki execution or Telegram delivery. Keiki's [channel docs](https://onkeiki.com/docs/channels) require an active plan for Telegram; a screenshot shows Starter active but key/workspace association and custom-tool runtime still need controlled verification. Free onboarding Live Test cannot run tools. The API gateway is separate from messaging.

Use the existing manually created Telegram channel entry; do not provision a duplicate or replace its webhook. Bot credentials belong only in secure runtime environment (`TELEGRAM_BOT_TOKEN_1` for the first bot; `_2`/`_3` are not used by this slice). No activation occurs in this code. A named executor must first verify workspace/key and existing channel/agent association, deploy reviewed combined source with ingress disabled, set tester bindings and server mapping, then obtain authorization to attach the existing bot and enable a tester-initiated DM. No purchase or unsolicited message is authorized.

Multiple Telegram `ref` identities per agent are documented, but the legacy tool envelope exposes no documented destination-bot/ref identifier and per-bot history isolation is unproven. Do not attach several bots to this one-agent mapping. Three existing channel entries do not prove isolation; separate agents under the same organization are only an alternative after account entitlement and key isolation are verified.
