# Offline ANSWER command seam

`parseVerifiedAnswer(envelope, binding, publicQuestionKeys)` is a pure parser, not a Convex endpoint. Its successful `command` type is extracted from Brain's generated internal dispatch signature. It neither claims a message nor calls dispatch/consult and is not connected to HTTP or the Keiki tool.

Grammar: `ANSWER d1q1: Your answer`. The keyword is uppercase ASCII, followed by one ASCII space, a case-sensitive public question key (1–64 ASCII letters/digits/underscores/hyphens, starting with a letter/digit), a colon, and optional one ASCII formatting space. The remaining answer is preserved verbatim, including Unicode, combining marks, whitespace and line breaks; no normalization, trimming or truncation is performed. Blank answers and additional line-leading ANSWER commands are rejected. Other commands are unsupported; no insight IDs or solution mappings are included.

Limits: 8,000 UTF-16 code units for raw text, 4,000 for the answer, 256 per envelope identifier. Emoji may use two code units. Lone surrogates, C0/C1 controls other than tab/CR/LF, and bidi embedding/isolate controls are rejected. Public question keys must come from the caller's authoritative recipient-visible session; unknown or duplicate matches return the same safe error. These checks do not replace Brain's case/day/segment entitlement checks.

The `caller-verified-provider-message` provenance marker is a caller assertion, **not cryptographic proof**. A future caller must first authenticate the provider and establish that raw text, event ID and private sender/conversation identity are platform-derived, not model tool arguments. It must resolve exactly one active private binding, provide its transport tuple and publicly available question keys, and separately keep the binding's player/group association. The parser checks exact transport equality; it cannot establish that a supplied binding is genuine, unique or private. No current Keiki HTTP payload has proven these raw-message primitives. `input.playerMessage`, summary, intent and model-visible sender text cannot supply this envelope.

Before dispatch, the future caller must atomically claim the event, preserve raw text, capture authoritative intakeCaseId/intakeDay and message association, and enforce replay/conflict handling. Brain requires an initial SF consult before commands, then dispatch's exact answerId is passed to consult; live binding and directive entitlement are rechecked on completion. None of this wiring is implemented here. The fixture Map in tests illustrates these obligations and cross-player denial only; it is not durable replay protection or provider authentication.
